## Security and release scope

- Guest orders resolve an active restaurant by slug. Products and categories must be active and scoped to that restaurant. The server obtains variant prices, fees and minimums from its own records and commits the order and price snapshots transactionally.
- The beta accepts Direct requests with only item identifiers and quantities. The server supplies fixed synthetic contact fields. Extra personal details, notes, client totals and WhatsApp submissions are rejected. Public Beta DTOs suppress the WhatsApp contact link. The standard checkout outside Beta retains its existing contact and WhatsApp behavior. Public catalog DTOs omit database credentials, session data and customer/order records. Keep the demo catalog synthetic and keep uploads and external fulfillment integrations off.
- Owner and Platform Admin have separate role checks and session namespaces. Sessions use hashed tokens and secure, HttpOnly, SameSite cookies. Authenticated mutations require an exact trusted Origin and a session-bound CSRF proof. Guest checkout uses an exact Origin allowlist and does not depend on a Savora login. Origin validation constrains browsers. Treat the endpoint as publicly callable by automated clients once exposed.
- The unique partial index on `{ restaurantId, idempotencyKeyHash }` and the normalized request hash handle same-key replays, changed bodies and concurrent requests. An identical request must return the original order. A changed payload under that key must return a conflict. The order identity is scoped to the tenant. Local tests cover request coordination and schema/route behavior. The live replay and conflict have not been performed.
- The current in-process limit is 10 attempts per minute per observed IP and slug in Beta, per function instance. Cold starts, independent instances, shared IPs and uncertain client-IP attribution limit its coverage. It is suitable only as a backstop for a small invited test on a protected URL with active monitoring and an operator able to pause ordering. A public link shared with invitees still admits anyone with that URL.
- The security review found that the draft applied the early delivery pause outside Beta. The corrected frontend applies it only in guarded Production Beta mode. The Beta UI also treats an edge deny as a pause and keeps the cart, while preserving separate handling for the app's exact untrusted-Origin rejection. Ordinary checkout still uses its existing contact flow, Origin error feedback and WhatsApp behavior.

## Proposed Vercel Firewall rules

The browser sends `POST /api/public/restaurants/savora-beta-demo/orders`. The root Service rewrite sends incoming `/api/(.*)` to Express, which mounts `POST /restaurants/:slug/orders` under `/api/public`. Match the incoming request path at the firewall before the Service rewrite.

Create these two rules in **food-delivery → Firewall → Configure → New Rule** after approval. For both rules, conditions are ANDed.

| Priority and name | Conditions | Action |
| --- | --- | --- |
| 1. Savora emergency checkout deny | **Method → Equals → POST**. **Request Path → Matches expression → `(?i)^/api/public/restaurants/[^/]+/orders/?$`**. | **Deny (403)**, per request with no persistent client action. Save as disabled during normal operation. |
| 2. Savora guest checkout rate limit | Same method and path conditions. | **Rate Limit → Fixed Window → 60 seconds → 5 requests → IP → Too Many Requests (429)**. Enable for normal operation. Leave response filters and persistent actions unset. |

The expression includes any restaurant slug and the optional trailing slash accepted by Express. It leaves GET menu traffic, OPTIONS preflight and all Owner/Admin paths outside the rules. Use no hostname or environment filter so every hostname attached to the project is covered, including the canonical public domain, staged Production, branch aliases, other generated URLs and protected Preview. Preview checkout POSTs intentionally share this protection. Both rules are project-local. Inventory any other project or direct ingress capable of writing to Beta and block or remove access there separately. The local route probe verifies the matcher and application route. Edge enforcement and hostname coverage must be verified after approved publication. [Vercel rule configuration](https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration)

Fixed-window IP counting and custom deny are supported on Hobby and Pro. Hobby permits one rate-limit rule within its three custom rules. Standard Pro permits up to 40 custom rules. Vercel tracks rate counts per region, so the proposed limit is not a global per-IP or tenant cap. All matching attempts count, including invalid requests and idempotent retries. Confirm the team's current included usage, regional pricing and any Edge Request or transfer charges. The operator must explicitly review the first-use **Rate Limiting Pricing** dialog and approve any billing change before publishing. [Vercel WAF limits and pricing](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) · [Usage and pricing](https://vercel.com/docs/vercel-firewall/vercel-waf/usage-and-pricing)
