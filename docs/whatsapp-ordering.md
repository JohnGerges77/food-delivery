# WhatsApp ordering

In **Owner Dashboard → Settings → Social Links**, enter the full number including its international calling code and enable **WhatsApp ordering**. The Owner API stores the canonical HTTPS link in `socialLinks.whatsapp` and the independent switch in `deliverySettings.whatsappOrderingEnabled`. Save and reload Settings to verify both. The switch defaults off for new and existing Restaurants. An existing social link stays saved. An Owner can turn off WhatsApp ordering and retain their number. Clearing the number also turns off WhatsApp ordering. Direct uses the existing delivery and deployment gates.

The Owner API validates the calling code and international number format. Format validation does not verify that a number is active on WhatsApp or owned by the restaurant. The Owner session and restaurant scope control updates, and PATCH still requires an exact trusted Origin and session CSRF. No MongoDB migration or index change is needed.

## Checkout and retries

- The public Restaurant DTO supplies `whatsappOrderingAvailable`. It derives from the saved number, the Owner’s opt-in, delivery availability, and deployment controls. A Beta DTO keeps the WhatsApp destination out of its social links.
- Both methods use `POST /api/public/restaurants/:slug/orders`, so the existing WAF match applies to both. Item, variant, price, tenant, Origin and rate checks still run on the API. The client supplies no destination or price.
- A WhatsApp success returns the saved reference, totals, `submissionMethod: "whatsapp"` and `whatsapp: { url, messageSent: false }`. The URL uses the transaction’s saved restaurant destination and order snapshots. The confirmation link can be opened again without posting. It is available when a popup is blocked. Long messages abbreviate labels to keep each item, variant, quantity and price in the link. Full snapshots remain in Owner Orders.
- A matching idempotency replay returns the original reference. If its destination is no longer allowed or has changed, it returns `whatsapp: { url: null, messageSent: false }`. A changed request under the same tenant and key returns `409`. Earlier links can still be opened by anyone who already saved them. Turning off WhatsApp ordering stops new handoff links and preserves saved Orders.

## Beta configuration

The guarded Production Beta backend accepts a server-only `SAVORA_BETA_WHATSAPP_TARGETS` environment value containing a JSON object from restaurant slugs to operator-owned numbers in canonical `+<country-code><number>` form. For example, use `{"your-test-slug":"+12025550100"}` as a shape illustration. The example number is reserved for fictional use. The operator must verify and supply their own approved number before staging. Keep the variable out of Preview and any `NEXT_PUBLIC_` configuration.

Missing or invalid policy data leaves Beta Direct available under its existing gates and disables Beta WhatsApp. Even an authenticated Owner cannot enable Beta WhatsApp for a different number or use another tenant's allowlisted number. A Beta checkout accepts only the selected method and item, quantity and variant identifiers. Savora synthesizes the stored contact fields. The generated message includes the bilingual test warning and order details without contact fields. Previewing it in Firefox requires no WhatsApp message or payment.

## Staging and Firefox acceptance

1. After separate approval to merge and deploy, verify the candidate SHA on `main`, the existing public alias, **Auto-assign Custom Production Domains** off, Vercel Authentication, the WAF rate rule and disabled emergency deny. Record the deployed rollback ID. Authorize any Production environment changes separately.
2. Stage a Git-backed **Production** deployment with the existing `savora_beta` credentials, existing checkout gate setting and the approved operator-owned number for the test tenant. Keep the generated URL protected and leave public aliases on the existing release. The Beta runtime requires the real Production `main` metadata. Check health, the deployment SHA, public alias and Owner/Admin `401` before signing in. Check that a missing allowlist or a disabled switch removes the option while Direct still follows its existing gates.
3. In authenticated Firefox, sign in as the test restaurant Owner on the staged URL. Save the approved number and enable WhatsApp ordering. Reload Settings and verify the saved number and switch. If delivery is closed, change it only when a live synthetic checkout test has been explicitly authorized. Record the baseline synthetic Order count.
4. Check English desktop and Arabic narrow layouts. In one authorized test session, select **Pizza Margherita → Medium × 1**, then **WhatsApp**. Confirm Beta shows no contact fields. In Firefox Network with logs preserved, expect one `201` response, a Pending reference, an EGP 200 item subtotal when the catalog still lists Medium at that price, and `messageSent: false`. Verify the same tenant, reference, variant, price and method in the Owner Orders dashboard and Atlas. Inspect the encoded handoff text and recipient. To test the fallback, allow Firefox to block the popup and verify the saved confirmation link renders. Reopen the composer for inspection only and leave **Send** untouched.
5. If the original POST is in Firefox Network, use **Edit and Resend** with the same body and key. Expect `200`, the same reference and the same Order count. A change to quantity with that key must return `409`. Opening the confirmation link must leave the count intact. With a valid Direct cart, verify selecting Direct avoids a WhatsApp handoff. A live Direct Order is a separate write.
6. Pause WhatsApp through its Owner switch if there is a destination or messaging issue. Stop both methods by disabling delivery or enabling the existing checkout POST emergency deny. Recheck the old public alias and obtain separate approval for manual promotion.
