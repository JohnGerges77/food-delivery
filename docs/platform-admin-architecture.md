# Platform Admin architecture (Phase 9)

The Platform Admin is a separate identity in `PlatformAdmin`, with an Argon2id password hash and a singleton bootstrap slot. It has no `restaurantId`. A dedicated `PlatformAdminSession` stores only SHA-256 hashes of a random session token and CSRF token. Its HttpOnly session cookie is named `savora_platform_session` and scoped to `/api/admin`; the readable CSRF cookie uses the same path. Owner cookies and Owner authentication continue to use their original models and `/api/auth` namespace. Every Admin API request checks the current Admin account and unexpired session in MongoDB. Logout deletes the session. Cookies are `Secure` in production and `SameSite=Lax`; write operations also require an exact trusted `Origin` and matching CSRF header. The login has a bounded in-process limiter. Production needs a shared limiter at the edge.

An operator creates the first Admin only through the interactive CLI. No HTTP bootstrap endpoint, startup bootstrap, public signup, or default credentials exist. The unique `bootstrapSlot` index and a precheck prevent concurrent or repeated bootstrap. The first account cannot be silently replaced. The single Admin identity fits V1; more administrators require a separately reviewed account lifecycle.

Admin restaurant creation validates strict inputs, hashes the Owner password, creates `Restaurant` and `User`, and inserts `PlatformAudit` inside one majority-write MongoDB transaction. A failure aborts all three writes. Unique database indexes enforce the slug and email. Status transitions use a conditional update and audit insert in the same transaction. Audits store action, Admin ID, restaurant ID, timestamp, and limited non-secret details. There is no password reset UI in Phase 9. Owner password management will need explicit session invalidation and a separate design.

Suspended tenants remain in the Admin list and can be reactivated. Public read endpoints return `404` for a suspended slug, yielding the storefront unavailable state; new checkout is rejected. Guest checkout writes the Restaurant version in its transaction so it conflicts with concurrent suspension. Owner login is denied, and every existing Owner session is checked against the current Restaurant status on each request. Historical orders and catalog records remain untouched. Records without a stored status are treated as active for compatibility.

The Admin UI lives under locale-aware `/en/admin` and `/ar/admin` routes. It has its own Zustand store and API client. It restores the Admin session before showing protected pages; Owner UI and credentials are separate. Arabic uses the root layout's local Tajawal font and RTL direction. Restaurant names remain user-provided text.

New index requirements: `platformadmins.email` unique; `platformadmins.bootstrapSlot` unique; `platformadminsessions.tokenHash` unique; `platformadminsessions.expiresAt` TTL; `platformaudits.restaurantId,createdAt`. Run read-only `npm run indexes:check` against the intended database before a separately approved rollout. Do not run `syncIndexes()` or drop collections. The first Admin bootstrap creates the Admin indexes; API tenant creation ensures Restaurant/User indexes before its transaction. Session and audit index rollout still needs the production deployment plan.
